P17：把模型页接到真接口，并修掉三个"看起来在跑"的缺陷

一、模型页面整页原来是假的（用户："模型页面完全不能做任何修改"）

`frontend/redesign/app.js` 里四份档案是**手抄的 JS 数组** `PROFILES`，「启用」只改内存变量，
「探活」用 `Math.random()` 编一个延迟和模型数再 `toast('探活成功')`，「思考」只改内存，
「新增档案」直接 `toast('演示版暂不写入')`。后端 `app/api/llm.py` 其实整套都在。

现在：列表来自 `GET /api/llm/profiles`，启用 = `POST /activate`（下一轮立刻生效），
拉清单 = `POST /models`，探活 = `POST /probe`（真发一次请求），新增/编辑 = `POST|PATCH`，
删除 = `DELETE`。顶栏、侧栏、输入框旁的模型名都来自同一份数据。
没有档案时如实显示"正在使用 · .env 默认值"，不编一份出来。

`PATCH` 每次都发整份字段 —— 因为后端 `update_profile` 是覆盖写，
只发改动的那几个会把 `note`/`num_ctx`/`base_url` 悄悄抹掉。

二、`OllamaClient.list_models` 从来没被绑到类上

`POST /profiles/{id}/probe` 对本地档案直接 500：`AttributeError: 'OllamaClient'
object has no attribute 'list_models'`。代码本身是对的，但它的缩进让它落在了
`context_truncation_note()` 的 `return` 之后 —— 语法合法、永不执行、也不是类的方法。
（`OpenAICompatClient` 的那份位置是对的，所以只有本地这一条路出事。）

`ModelLister` 协议还漏了 `@runtime_checkable`，而 `api/llm.py` 用
`isinstance(client, ModelLister)` 判断能力 —— 少了它，每次判断都抛 TypeError，
"列模型"对所有服务商都是 500。

新增 `tests/agent/test_llm_lister.py`：测的不是解析逻辑，而是**方法到底在不在类上**。

三、讨论在跑的时候改设置会 500（database is locked）

SQLite 默认 rollback journal + `busy_timeout=0`，而这里有一类特别长的写事务：
讨论在等模型回答的那几十秒。现在开 WAL（读写不互相阻塞）并给 5 秒 busy_timeout。

四、验证（都跑过）

- 全量 suite：1449 passed（原 1446，+3）
- `var_ref/probe_model_page.py`：拉清单 9 个模型、探活 `ok=True`、
  连问两句得到两个不同的回答（其中一轮带真实工具调用 `ask_about_task`）
- `var_ref/check_model_page.mjs`：无头 Edge 读 DOM 与 `/api/llm/*` 对照 ——
  档案行数、当前印鉴、顶栏模型名、页面无报错，退出码 0

五、如实记下还没解决的

- 默认的 `qwen3.6:27b`（17 GB）在这台机器上**起不来**（llama-server 报
  `ggml_vulkan: Failed to allocate pinned memory`）。现在生效的是 `qwen3.5:9b`。
- 9B 的第一轮（模型要进显存 + 整份工具声明）实测撞到 300 秒超时，第二轮才答；
  这是性能问题，不是链路问题 —— 界面上那一轮会照实报"timed out"。
- 澄清问题（`ask_about_task`）仍然没有界面列表，后端也没有对应端点。
